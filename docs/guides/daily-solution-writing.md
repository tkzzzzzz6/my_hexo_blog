# 每日一题写作规范

适用于本博客的 LeetCode、洛谷、牛客、Codeforces 等单题题解。目标读者已经看过题目，希望快速理解关键思路、必要公式，并对照代码实现。评价标准是读完能解释“为什么这样做、如何写出来”，不是文章或代码越短越好。

认可的示范：[2333 · 最小差值平方和](../../source/_posts/daily/2026-10-10-LeetCode刷题笔记-2333-最小差值平方和.md)。参考它的信息取舍和段落组织，不以它的字数或章节数作为硬指标。

## 1. 单题题解与知识总结

| 内容 | 每日一题 | 总结性文章 |
| --- | --- | --- |
| 题意 | 原题链接 + 简短目标与关键约束 | 按主题组织，不逐题复述 |
| 思路 | 本题关键观察、推导、实现方式 | 通用模型、适用条件、方法比较 |
| 论证 | 支撑当前解法的必要论证 | 系统证明、原理展开与反例集 |
| 代码 | 默认一份主解法，语言按用户要求或已有代码；未指定时优先 C++ | 按比较目的选择多种实现 |
| 示例 | 只选能澄清本题难点的例子 | 系统练习、变式与延伸 |

本题正确性依赖的贪心交换、单调性或状态转移依据必须在题解中讲清。若理解它需要较长推导，就保留相应篇幅。泛化的知识讲义、多解比较、完整题单放在总结文章；已有总结可链接，没有则只在交付说明中列为后续选题，不编造文章链接，不自动扩大本次任务。

明确要求写专题教程、算法总结或多解比较时，按其教学目标展开，不套用单题精简结构。

## 2. 推荐的阅读顺序

以下是默认起点，标题可按题目调整，相关内容可合并，不要求凑齐固定章节：

1. **题目链接与简短题意**：说清求什么，以及影响解法的条件，如“至多”还是“恰好”、数值范围、能否重复操作。无需复制完整题面和全部样例。
2. **思路**：先给关键观察，再说明为什么成立，最后衔接算法步骤与代码。必要公式在这里出现。
3. **代码**：一份完整可提交的主解法，与前文变量、循环和处理顺序对应。
4. **复杂度与边界**：定义复杂度中的变量，给出时间、空间复杂度，以及本题真正影响实现的边界。也可以把边界直接放在相应推导旁。

可以像 2333 一样只设“思路、代码、复杂度与边界”三节。Hexo 已渲染文章标题，正文不要求再写 H1；章节不要求 emoji。小段文字直接连贯叙述，长内容再分小节。

## 3. 思路如何写得精炼而完整

- **开头落到本题观察。** 例如 2333 从差值和操作预算入手，而不是先介绍贪心算法的历史或定义。
- **每个公式承担一步推导。** 首次出现时定义变量，说明适用条件和它带来的决定。2333 的 `2x - 1` 用来解释为何优先削减最大的差值，不是单独摆放一个结论。
- **把“为什么”接到“怎么做”。** 例如二分答案需说明判定为何单调、范围如何确定；动态规划需交代状态、转移和初值；贪心需给出本题成立的理由。
- **一段解决一个问题。** 避免在“初步思路、算法分析、正确性、总结”里重复同一观察。只有真正存在两步不同推导时才拆节。
- **按难点选辅助材料。** 读者易混淆的状态变化可加一个小例子或示意图；不为满足模板强加表格、图片、样例表或题后感想。

不设置统一字数上限。简单题可以很短，复杂题应给足推导；删的是重复内容和偏离本题的展开。

## 4. 代码以可读性为准

- 保留清晰的变量名、正常换行、阶段间空行和解释意图的注释。无需把多个操作压成一行或使用难懂的缩写。
- 保留有助于理解、简化后续流程的边界分支。例如 2333 的 `sum <= k` 提前返回可以直接表达“预算足以清零”，不因省变量或行数而删除。
- 已认可且正确的代码，默认保持算法和可读结构；文字精简不等于代码重构。若要改变算法或边界处理，需重新验证。
- 代码与讲解保持一致，注意整数宽度、初值、下标及平台接口。默认只提供一种语言的一种主解法；用户明确要求多解或多语言时再展开。
- 代码块标注实际语言，如 `cpp`、`python`、`go`。复杂度必须按最终实现计算，包含排序、桶范围和辅助存储等成本。

## 5. 落盘与验证

- 正式文章写入 `source/_posts/` 下，单题优先沿用现有 `daily/` 目录和文件命名。编辑旧文保留文件名、日期、永久链接、分类标签与评论 pathname；调整这些元数据需要另行确认范围。
- 新文补齐 `title`、`date`、`categories`、`tags`，按仓库约定取值；以实际题目来源核对题号、链接和关键条件。
- 公式用现有 Markdown/LaTeX 写法，代码块标明语言。表格只用于实际比较。需要配图时按图床流程上传，临时图片和验证文件留在 ignored `tools/blog-assets/`。
- 验证最终正文中的实际代码，按题目选择官方样例、关键边界，必要时独立暴力对拍；若用户明确要求自行测评，遵从其安排。检查公式、代码块和链接的生成结果。
- 验证证据写在交付说明或 PR 中。正文不堆编译日志、Agent 工作过程，不写未经实际执行支持的“全部测试通过”。格式检查不能代替算法正确性检查；未执行的验证明确说明。
- 提交前按仓库流程运行 lint、测试和构建。写文章不包含发布授权，最终交付按仓库的 PR 流程办理。

交付前快速检查：

- [ ] 读者能顺着“观察 → 理由/公式 → 算法 → 代码”理解本题。
- [ ] 必要论证齐全，章节与段落没有重复解释同一件事。
- [ ] 一份清晰主解法，变量和边界处理与讲解对应，复杂度准确。
- [ ] 辅助例子、表格、图片确实解决理解问题；没有为了模板补章节。
- [ ] 题目链接、元数据、渲染和验证范围已检查，外链总结确实存在。

## 6. 放在哪里、怎样使用

**本文件是本仓库单题写作规则的唯一正文来源**，纳入 Git 和 PR 维护，放在 `docs/guides/`，不作为博客文章发布。根目录 `AGENTS.md` 提供任务入口；项目的 `.github/skills/blog-post-writer/SKILL.md` 及算法模板指向这里，避免各自复制一套规定。

在仓库内直接要求：

```text
按 docs/guides/daily-solution-writing.md，为 LeetCode xxxx 写一篇每日一题。
重点讲思路和关键公式，代码保持清晰；通用知识只链接已有总结。
```

编辑旧文时指出具体文件和范围：

```text
按每日一题写作规范整理 source/_posts/daily/<文章>.md。
保留当前代码和元数据，主要精简重复讲解、调整排版。
```

本机使用 `cs-blog-writer` 时，可写 `$cs-blog-writer 按本仓库每日一题规范整理……`；该 skill 应先读取仓库规则。换电脑需同步个人 skill 的适配入口，仓库规则本身随 Git 同步。没有配置个人 skill 时，直接引用本文件即可；不要假定所有工具都会自动加载 `.github/skills/`。

本规范只影响当前任务涉及的文章，不自动批量改写历史题解。更新规范后在同一个交付 PR 中说明变更，维护者合并后供后续任务使用。
