
## 第一章 软件工程概述

### 1. 什么是软件？软件有哪些组成？

软件是运行在计算机等设备上、实现特定功能的程序、数据与相关文档的总称，由三部分组成：

- **程序**：逻辑指令集合，是功能实现的核心载体
- **数据**：程序处理与存储的信息  
- **文档**：用于需求、设计、使用与维护说明

> **关键理解**：从软件开发角度，程序最重要（是功能落地的关键），但从维护角度，文档也极为重要（是开发团队之间的沟通桥梁）

---

### 2. 软件的主要特点是什么？

软件是复杂的抽象逻辑产品，主要特点为：

| 特点                   | 说明                         |
| ---------------------- | ---------------------------- |
| **脑力劳动的不可见性** | 不像硬件有实体，难以直观评估 |
| **规模大且复杂**       | 规模越大，开发维护难度越高   |
| **易变性**             | 需要随需求变化不断修改       |
| **维护困难**           | 因频繁修改而变得难以维护     |

---

### 3. 什么是软件危机？

软件危机是指在软件开发和维护过程中所遇到的一系列严重问题。主要表现为：

1. **开发问题**：在需求增长、规模扩大的情况下，难以高质量、按时完成软件开发

2. **维护问题**：对数量膨胀、结构复杂的已有软件难以进行有效维护和升级

---

### 4. 软件危机的典型表现有哪些？

| 表现                     | 具体例子                                       |
| ------------------------ | ---------------------------------------------- |
| **成本和进度估计不准确** | 算法复杂度预估不足，导致项目延期和成本超支     |
| **用户不满意**           | 超市库存系统不符合操作习惯，上线3个月被迫回滚  |
| **软件质量不可靠**       | App更新后出现大规模闪退、消息异常              |
| **软件不可维护**         | 项目扩大导致代码混乱，性能瓶颈，只能整体重构   |
| **缺乏文档**             | 独立游戏项目无接口文档，核心团队离职后难以接手 |
| **软件成本逐年上升**     | 硬件成本下降，软件成本反而上升（谷歌GFS例子）  |
| **生产率跟不上需求**     | AI应用爆发，开发人才紧缺，项目排队等待         |

---

### 5. 产生软件危机的根源是什么？

**根源一：软件本身的特点**
- 软件是智力密集型、规模庞大、能见度低的复杂产品
- 其固有的易变性和维护困难增加了开发和管理的难度

**根源二：开发与维护方法的不正确**
- 将软件与程序混为一谈
- 缺乏软件生命周期的阶段性概念  
- 导致管理混乱、维护困难

---

### 6. 如何消除软件危机？

**四个关键措施：**

1. **正确认识软件**：认识到软件 = 程序 + 数据 + 文档（不是单纯代码）

2. **工程化思维**：软件开发是组织严密、分工明确、团队协作的工程项目（不是个人英雄主义）

3. **推广成熟技术**：积极推广和应用在实践中总结出的有效技术和方法

4. **工具化辅助**：开发和使用先进的软件工具，提高开发效率和质量

**总结**：通过 **工程化、规范化和工具化** 的手段，才能从根本上缓解和消除软件危机

---

### 7. 什么是软件工程？

软件工程是一门应用工程化原则、方法和技术来开发和维护软件的学科。

**核心特征：**
- 将系统的、规范的、可量化的方法应用于软件全生命周期
- 融入工程化思想
- 目标：提高质量、提升可维护性、降低成本

---

### 8. 软件工程的基本目标是什么？

**质量保证**

---

### 9. 软件工程的三要素是什么？

| 要素     | 定义                             | 作用                         |
| -------- | -------------------------------- | ---------------------------- |
| **方法** | 完成软件开发各项任务的技术手段   | 为开发提供"怎么做"的技术指导 |
| **工具** | 辅助软件开发的软件或硬件         | 提升开发效率和质量           |
| **过程** | 将方法与工具深度融合的标准化流程 | 建立可控的、一致的开发准则   |

**理解**：三要素缺一不可，过程是将方法和工具有机结合的框架，确保开发的规范性和可控性

---

### 10. 软件工程有哪7条基本原理？

1. **分阶段管理**
   - 将软件生命周期划分为多个阶段，制定规范的计划并严格执行

2. **进行阶段评审**  
   - 在每个阶段结束时进行评审，尽早发现问题

3. **实行严格的产品控制**
   - 对软件需求和变更进行严格管理，避免无序变更

4. **采用现代程序设计技术**
   - 使用面向对象、模块化等先进技术，提升可维护性

5. **结果应能清楚地审查**
   - 每个阶段的成果都要具备可审查性

6. **开发小组人员应少而精**
   - 小型团队沟通效率高，更容易协调管理

7. **承认不断改进的必要性**
   - 持续学习和引入新的技术、方法，提升整体水平

---

### 11. 什么是软件生命周期？

软件生命周期是指将软件的开发与维护过程划分成若干个阶段，并相应地制定出切实可行的计划，然后严格按照计划进行管理的全过程。

**涵盖范围**：从提出设想、开始开发，到投入使用、持续维护，直至最终退役的整个历史演化过程

**三个时期**：
1. **软件定义** - 问题定义、可行性研究、需求分析
2. **软件开发** - 总体设计、详细设计、编码和单元测试、综合测试
3. **运行维护** - 维护和优化

---

### 12. 标准的软件生命周期分为哪3个时期，哪8个阶段？

| 时期           | 阶段              | 核心任务   | 输出             |
| -------------- | ----------------- | ---------- | ---------------- |
| **软件定义期** | 1. 问题定义       | 明确问题   | 立项说明书       |
|                | 2. 可行性研究     | 评估可行性 | 可行性报告       |
|                | 3. 需求分析       | 确定需求   | 需求规格说明     |
| **软件开发期** | 4. 总体设计       | 架构设计   | 架构图           |
|                | 5. 详细设计       | 模块设计   | 流程图           |
|                | 6. 编码和单元测试 | 编码测试   | 源代码和测试报告 |
|                | 7. 综合测试       | 集成验证   | 综合测试报告     |
| **运行维护期** | 8. 维护           | 持续优化   | 维护日志         |

---

### 12. 什么是软件过程？用4个英语单词总结

**软件过程的四个要素**：
- **Who** - 谁来做（人员）
- **When** - 什么时候做（时间）
- **What** - 做什么（任务）
- **How** - 怎么做（方法）

---

### 13. 列举常见的几种软件过程模型

| 模型名称         | 定义                                   | 特点                                 | 适用范围                 |
| ---------------- | -------------------------------------- | ------------------------------------ | ------------------------ |
| **瀑布模型**     | 按阶段顺序进行，各阶段依次完成         | 线性、文档规范、需求变更困难         | 需求明确且稳定、规模较小 |
| **快速原型模型** | 快速构建原型，与用户不断交流完善需求   | 开发快、用户参与度高、能快速验证需求 | 需求不明确、界面交互较多 |
| **增量模型**     | 系统划分为多个功能模块，逐步开发交付   | 分阶段实现、每版本可运行、风险低     | 规模较大、功能可逐步实现 |
| **螺旋模型**     | 结合瀑布和原型模型，强调风险分析       | 迭代开发、风险控制好                 | 大型复杂、高风险项目     |
| **喷泉模型**     | 面向对象，各阶段可交叉进行             | 灵活、支持迭代、可重叠               | 面向对象的软件开发       |
| **RUP统一过程**  | 迭代式框架，用例驱动、以体系结构为中心 | 包括初始、细化、构建、交付四阶段     | 中大型面向对象系统       |
| **敏捷过程**     | 强调快速迭代和持续交付                 | 周期短、反馈快、适应变化强           | 需求变化频繁的项目       |

## 第二章 可行性研究

---

### 1. 可行性研究的目的是什么？

以最小的代价在最短的时间内 **确定项目是否可能开发、是否值得开发**，从而避免盲目投资和不必要的损失。

**核心理念**：可行性研究的目的不是解决问题，而是确定 **问题是否值得去解决**。

---

### 2. 可行性研究的本质是什么？

**本质**：是一个大大压缩简化了的系统分析和设计过程

**特点**：通过最小化的投入来预判项目的可行性

---

### 3. 可行性主要涉及哪些方面？

| 可行性         | 核心问题                         | 判断标准                                         |
| -------------- | -------------------------------- | ------------------------------------------------ |
| **技术可行性** | 当前技术水平是否能支撑项目实现？ | 是否存在技术瓶颈；现有技术能否实现               |
| **经济可行性** | 项目的成本与预期收益是否合理？   | 经济效益是否超过开发成本；投资回报率是否符合预期 |
| **操作可行性** | 系统操作流程是否符合用户习惯？   | 系统是否易于用户理解和高效使用                   |

---

### 4. 可行性研究的完整过程是什么？

可行性研究一般分为 **3个步骤**：

1. **确定系统的目标范围**
   - 明确项目的目标和边界

2. **提出解决方案**
   - 分析可能的技术、经济、操作方案

3. **编制可行性报告**
   - 形成正式的评估文档

---

## 第三章 需求分析

### 1. 需求分析的目的和任务是什么？

**目的**：弄清楚 **"系统必须做什么"**

**任务**：
1. 明确对系统的综合要求
2. 分析系统的数据要求
3. 导出系统的逻辑模型
4. 修正系统开发计划

---

### 2. 需求分析一般要经历哪几个步骤？

| 步骤            | 任务                                     | 输出                      |
| --------------- | ---------------------------------------- | ------------------------- |
| **1. 获取需求** | 与客户沟通、调研，挖掘用户的真实期望     | 收集到的需求信息          |
| **2. 分析建模** | 将信息进行梳理、归纳和逻辑抽象           | 用例图、数据流图等模型    |
| **3. 需求描述** | 将需求以标准化、严谨的文字编写成正式文档 | 软件需求规格说明书（SRS） |
| **4. 需求验证** | 邀请相关方共同评审需求文档               | 验证文档准确无误          |

---

### 3. 如何获得需求？有哪些方式？

**主要方式**：
1. 访谈
2. 实地操作和观察
3. 简易的应用规格说明技术
4. 快速建立软件原型

**本质概括**：归根到底可以用一个词表示——**"沟通"**

---

### 4. 需求分析时一般需要建立哪三种模型？

| 模型         | 呈现形式   | 作用                                           |
| ------------ | ---------- | ---------------------------------------------- |
| **数据模型** | E-R图      | 梳理系统数据对象及关联，为数据存储管理提供依据 |
| **功能模型** | 数据流图   | 明确系统功能及数据流转，定义系统要"做什么"     |
| **行为模型** | 状态转换图 | 描述系统在外部事件下的状态变化与响应           |

---

### 5. 需求分析建模时的原则有哪几条？

1. **问题抽象** - 只抽取本质，屏蔽非本质细节
2. **问题分解** - 将复杂问题分解为若干个相对简单的子问题
3. **多视点** - 从不同角度分析和描述系统

---

## 第四章 形式化论

### 1. 什么是形式化方法？有什么优缺点？

**定义**：形式化方法是描述系统性质的基于数学的技术

**应用例子**：
- 学数据库时，用符号定义与逻辑推理描述关系结构
- 用Armstrong公理求属性闭包和最小依赖集
- 用形式化标准判断范式等级
- 验证模式分解的无损连接性和保持函数依赖性

## 第五章 总体设计

### 1. 软件设计的目的与任务是什么？

**核心目的**：实现从 **"做什么"** （需求层面）到 **"怎么做"** （实现层面）的转化

**具体任务**：
- 将需求分析阶段确定的软件需求转化为指导具体构建的软件表示与实施方案
- 为后续的开发工作提供清晰、可执行的系统模型

---

### 2. 软件设计主要包括哪些设计？

1. 过程设计
2. 接口设计
3. 系统结构设计
4. 数据设计

---

### 3. 软件设计的两个阶段及主要任务

| 阶段         | 也称为            | 主要任务                                                                                                                           |
| ------------ | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **第一阶段** | 概要设计/总体设计 | ✓ 建立软件系统的整体架构<br>✓ 模块划分和功能定义<br>✓ 确定模块间调用关系<br>✓ 全局数据结构和数据库设计                             |
| **第二阶段** | 详细设计/过程设计 | ✓ 对每个模块进行细化<br>✓ 设计具体的执行算法<br>✓ 设计内部运行逻辑流程<br>✓ 定义模块局部数据结构<br>✓ 输出可直接指导编码的详细说明 |

---

### 4. 解释核心概念：模块

**模块**：程序对象有名字的集合

**包括**：过程、函数、子程序、宏等

**地位**：是构成软件系统结构的基本元素

---

### 5. 什么是模块化？

**目标**：采用 **分而治之** 的思想，减少问题的复杂度

**方法**：将系统划分为若干个模块，每个模块完成一个子功能，通过模块间的联系构成完整的软件整体

---

### 6. 什么是抽象？

**定义**：抽象是应对软件复杂性的基本思维工具

**本质**：只抽取本质，不关心形式；屏蔽非本质细节的过程

**例子**：编程语言中的接口、抽象类或数据类型

**作用**：有效降低系统的认知与设计难度

---

### 7. 什么是逐步求精？

**定义**：与"抽象"互补的核心策略，将宏观问题逐层分解并不断细化具体细节的过程

**应用**：从总体架构划分最终落实到具体代码编写

**指导原理**：确保开发者在每个设计阶段处理的信息量控制在 **Miller法则** （7±2个组块）之内

**意义**：平稳、可控地将总体设计转化为最终的底层实现

---

### 8. 什么是信息隐藏？

**定义**：提升软件可维护性的关键设计准则

**本质**：对模块内部的过程细节和局部数据施加访问限制的过程

**例子**：面向对象编程中的封装、局部变量的引用

**作用**：避免外部模块的直接干扰与不必要依赖，确保局部修改不会传播到系统其他部分

---

### 9. 什么是模块独立性？如何度量？

**定义**：综合了模块化、抽象和信息隐藏等设计思想的系统划分标准

**度量方法**：通过衡量以下两个定性指标：
- **"耦合"** - 衡量模块间的相互依赖程度（越低越好）
- **"内聚"** - 衡量模块内部各成分的结合程度（越高越好）

**核心原则**：**紧内聚、松耦合**

---

### 10. 什么是内聚？有哪些分类？

**定义**：衡量一个模块内部各元素（代码、数据等）之间结合紧密程度的定性指标

**反映**：模块功能的专一性（模块是否专注于只做一件事）

**分类**（由弱到强，共7种）：
1. 偶然内聚
2. 逻辑内聚
3. 时间内聚
4. 过程内聚
5. 通信内聚
6. 顺序内聚
7. **功能内聚**（最强）

---

### 11. 什么是耦合？有哪些分类？

**定义**：衡量软件系统中不同模块之间相互依赖和连接紧密程度的定性指标

**反映**：模块间的独立性（一个模块对另一个模块运作细节的依赖程度）

**分类**（由弱到强，共7种）：
1. 非直接耦合
2. 数据耦合
3. 特征耦合
4. 控制耦合
5. 外部耦合
6. 公共耦合
7. **内容耦合**（最强，最坏）

---

### 12. 模块独立的原则是什么？

**核心原则**：**紧内聚、松耦合**

**含义**：
- 模块内部功能紧密结合
- 模块之间依赖尽量少、接口尽量简单

---

### 13. 如果一个软件有几十个模块，其中有6个模块存在完全相同的部分（控制结构和数据结构），如何重组？

**问题分析**：
- 代码冗余严重，增加程序体积和开发成本
- 维护性差，需要逐一修改，容易出现遗漏和不一致
- 模块复用性差

**解决方案**：
1. 将6个模块中相同的部分提取出来，封装成一个独立的公共基础模块
2. 原有的6个模块只保留各自特有的业务逻辑
3. 统一调用这个公共模块

**效果**：减少冗余、统一维护、提升复用性

---

### 14. 如果6个模块的控制结构相同，仅处理的数据不同，如何重组？

**解决方案**：
1. 将相同的控制结构提取出来，封装为可复用的通用模块
2. 将原6个模块中差异化的处理数据作为该通用模块的 **输入参数**
3. 原6个模块仅保留对数据的准备工作
4. 最终调用通用模块完成功能

**效果**：消除代码冗余、降低维护成本、提升程序可扩展性

---

### 15. 软件模块的大小如何度量？量化指标是什么？

**度量标准**：模块包含的代码行数

**量化指标**：一般在 **10至60行代码** 之间比较合适

---

### 16. 过大的模块有什么问题？过小的模块呢？

| 问题类型       | 具体问题                       | 解决方案               |
| -------------- | ------------------------------ | ---------------------- |
| **过大的模块** | 可理解程度迅速下降             | 充分分解过大模块       |
| **过小的模块** | 开销大于有效操作，系统接口复杂 | 将小模块合并到上级模块 |

---

### 17. 划分模块的最基本原则是什么？

**最基本原则**：**高内聚、低耦合**

**具体内涵**：
- **高内聚**：一个模块的功能应围绕同一目标、职责尽量单一、内部元素联系紧密
- **低耦合**：模块间依赖尽量少、接口尽量简单

**核心意义**：不能只看模块"大小"，更要看职责集中度和依赖复杂度，实现易理解、易测试、易维护和易扩展

---

### 18. 什么是扇入度和扇出度？高扇入和高扇出的危害？

| 指标       | 定义                     | 风险                                                   | 解决方法                                                         |
| ---------- | ------------------------ | ------------------------------------------------------ | ---------------------------------------------------------------- |
| **扇入度** | 调用某模块的上层模块数量 | 该模块一旦有缺陷，会产生大范围连锁影响，增加回归成本   | 通过高内聚低耦合重构职责边界；减少不必要依赖                     |
| **扇出度** | 某模块调用下层模块的数量 | 模块职责过大、耦合过高、理解和测试困难、对外部变化敏感 | 使用分层设计和门面接口收敛调用关系；对高扇入核心模块保持接口稳定 |

---

### 19. 什么是控制域？什么是作用域？

| 概念       | 定义                                           |
| ---------- | ---------------------------------------------- |
| **控制域** | 某个控制结构或模块能够直接支配与约束的程序范围 |
| **作用域** | 某个数据、状态或处理结果实际产生影响的范围     |

**原则**：原则上要求 **作用域应该在控制域之内**

**问题**：该原则主要解决的是 **控制与影响范围不一致导致的逻辑混乱、数据污染、缺陷定位困难和维护风险上升问题**

**效果**：提升程序可理解性与可验证性

---

### 20. 如何理解和降低接口的复杂性？

**接口复杂性的表现**：
- 参数数量多
- 参数结构深
- 调用顺序和状态约束多
- 异常与返回语义不清
- 隐式依赖多

**危害**：接口越复杂，调用方越容易误用并引入集成错误

**降低方法**：
- 减少参数与接口数量
- 明确输入输出与异常契约
- 统一数据模型与命名规范
- 封装变化细节，避免暴露内部实现
- 接口分层、版本管理和文档化约束
- 保持接口长期稳定

---

### 21. 什么是SD方法？它要做什么？

**SD方法**：结构化设计方法

**定义**：在需求分析和结构化分析的基础上，把系统逻辑模型进一步转换为软件体系结构和模块结构的设计方法

**任务**：
- 把系统功能逐步分解、细化和组织成若干高内聚、低耦合的模块
- 确定模块间的调用关系、接口关系和控制关系
- 为后续详细设计与编码实现提供清晰的结构蓝图

---

### 22. 什么是变换流？

**定义**：数据沿着"输入变换区、中心变换区、输出变换区"线性加工路径逐步完成转换的一类信息流

**构成**（三部分）：
1. **输入部分** - 接收和预处理数据
2. **变换中心** - 完成核心加工和转换
3. **输出部分** - 整理并输出结果到外部

**典型应用**：编译程序、数学计算程序、文档转换程序、深度学习等科学计算程序

---

### 23. 什么是事务流？

**定义**：系统接收一个事务请求后，进入事务中心判定，再根据不同分支分别执行不同处理的一类信息流

**构成**（多部分）：
- 事务中心 - 识别事务类型，控制流程转向
- 多个分支处理路径 - 分别处理不同类型事务

**特点**："一个入口、多条分支、按事务类型分别处理"

**典型应用**：操作系统命令处理程序、数据库事务处理、订票系统、银行业务处理、菜单驱动式应用

---

## 第六章 详细设计

### 1. 结构程序设计的六个核心方面

1. **限定基本的控制结构**
   - 只使用：顺序、选择（分支）、循环（重复）

2. **坚持单一入口和出口**
   - 每一个控制结构只准许有一个入口和一个出口

3. **采用组合与嵌套**
   - 复杂结构通过基本控制结构进行组合嵌套实现

4. **严格限制GOTO语句**
   - 除非特别强调效率，一般不使用

5. **适当使用扩展控制结构**
   - 如直到循环、多路分支等

6. **有条件地改变程序流程**
   - 在不影响清晰可读且强调效率的前提下，可使用continue和break等

---

### 2. 设计人机界面要考虑的主要因素

**用户特性方面**：
- 用户的熟练度
- 操作频度
- 知识水平
- 生理特点

**交互需要注意**：
- 系统响应时间
- 用户帮助设施
- 出错信息处理
- 命令交互

## 第七章 实现 - 优化版

### 1. 什么是软件测试？目标是什么？

**定义**：为了发现程序中的错误而执行程序的过程

**本质**：通过刻意执行程序来暴露出潜在的问题

**目标**：
- 发现软件中的错误
- 开发出高质量、符合需求的软件
- 提高软件的可靠性

---

### 2. 软件测试的核心原则

1. **追溯到用户需求**
   - 所有测试都应能追溯到用户需求

2. **提前计划**
   - 应在需求完成就开始制定测试计划
   - 在设计完成后就开始设计测试方案

3. **应用Pareto原理**
   - 80%的错误来自20%的模块
   - 应重点测试可疑的模块

4. **从小到大**
   - 从模块测试 → 模块簇测试 → 系统测试

5. **穷举测试不可能**
   - 即使中等程序，执行路径排列数也十分庞大
   - 测试只能证明有错误，不能证明没错误

6. **独立第三方测试**
   - 开发人员不是最佳测试人选
   - 应由独立的第三方从事测试工作

---

### 3. 软件测试的两种方法

| 方法         | 关注点                               | 原理                                           |
| ------------ | ------------------------------------ | ---------------------------------------------- |
| **黑盒测试** | 不关心内部代码实现，只关注输入和输出 | 根据需求规格说明，输入数据检查输出是否符合预期 |
| **白盒测试** | 基于程序内部代码结构和逻辑           | 了解代码实现，检查执行路径、分支覆盖等         |

---

### 4. 什么是测试用例？

**定义**：测试用例 = 输入数据 + 预期结果

**说明**：根据测试目的和选择的测试方法而设计的输入数据，以及与之对应的预期结果的集合

---

### 5. 软件测试的步骤

| 步骤                          | 定义                                                 | 测试类型    |
| ----------------------------- | ---------------------------------------------------- | ----------- |
| **1. 模块测试（单元测试）**   | 编码完成后对模块进行的测试，重点在模块内部及接口部分 | 白盒测试    |
| **2. 子系统测试（集成测试）** | 将多个相关模块组合成子系统进行测试                   | 白+黑盒混合 |
| **3. 系统测试**               | 完整软件系统与计算机硬件、外设等整体测试             | 黑盒测试    |
| **4. 验收测试（确认测试）**   | 以SRS为标准，需用户参与，验证软件有效性              | 黑盒测试    |
| **5. 平行运行**               | 新系统与旧系统在相同环境下同时运行，比对结果         | 确认测试    |

---

## 第八章 软件维护

### 1. 什么是软件维护？为什么要维护？

**定义**：在软件交付后，为了改正错误或满足新的需要而修改软件的过程

**维护目的**：
- 提高软件的可维护性
- 减少软件维护所需的工作量
- 降低软件系统的总成本

**占比**：软件维护在生命周期中占比约 **65%-70%**

---

### 2. 软件维护分为哪几类？

| 类型           | 占比 | 定义                                     |
| -------------- | ---- | ---------------------------------------- |
| **完善性维护** | 50%  | 为了满足用户不断增长的功能与性能需求     |
| **适应性维护** | 25%  | 使软件适应外部环境（OS、硬件等）的变化   |
| **改正性维护** | 20%  | 纠正开发时期遗留、交付后才暴露的错误     |
| **预防性维护** | 5%   | 提高可靠性和可维护性，为未来修改奠定基础 |

---

### 3. 什么是软件的可维护性？

**定义**：维护人员理解、改正、改动或改进这个软件的 **难易程度**

---

### 4. 软件可维护性的定性指标有哪些？

共5个定性指标：

1. **可理解性** - 代码是否易于理解
2. **可测试性** - 是否易于测试
3. **可移植性** - 是否易于移植到其他平台
4. **可修改性** - 是否易于修改和扩展
5. **可重用性** - 是否能复用到其他项目

---

### 5. 如何提高软件的可维护性？

**一句话总结**：坚持使用 **科学的软件工程方法和工具**

---

## 第九章 面向对象的方法学引论

### 1. 什么是面向对象方法？核心概念有哪些？

**定义**：类似人的思维方法，通过对象、类、继承、消息通信等方法来组织代码，把数据和操作数据的方法封装在一起

**核心概念**：
- 封装（Encapsulation）
- 继承（Inheritance）
- 多态（Polymorphism）
- 抽象（Abstraction）

---

### 2. 面向对象方法有哪些优点？

1. **与人类习惯的思维方式一致** - 更直观自然

2. **稳定性好** - 相比面向过程更稳定

3. **可重用性好** - 类和对象易于复用

4. **较易开发大型软件产品** - 适合复杂系统

5. **可维护性好** - 代码结构清晰，便于维护

---

## 第13章 软件项目管理

### 1. 什么是管理？

**定义**：通过计划、组织和控制等一系列活动，合理地配置和使用各种资源，以达到既定目标的过程

**核心要点**：
- 计划的实施和验收
- 各流程需要有不同的量化指标
- 目标是提高效率

---

### 2. 软件项目管理的主要方面有哪些？

#### **① 软件开发成本管理**
- 进行软件规模估算
- 方法：自顶向下、自底向上、专家估算法等
- 技术：代码行、功能点、COCOMO2模型等
- 作为估算时间、人员和经费的基础

#### **② 控制与进度计划**
- 定义项目中的全部任务
- 识别出关键任务
- 规定各项任务的起止日期
- 工具：Gantt图、任务网络图等
- 及时发现拖延进度的情况

#### **③ 开发人员与组织机构管理**
- 根据项目特点建立有凝聚力的项目组
- 民主制程序员组、主程序员组等
- 注意："单纯增加人员并不能提高效率"
- 合理配置人力资源

#### **④ 用户管理**
- 将用户作为管理的重要一环
- 确保项目实施达到既定目标
- 让用户满意

#### **⑤ 软件开发文档与配置管理**
- 在整个生命周期内进行配置管理
- 追踪和控制程序、文档和数据的变化
- 包括：标识、版本控制、变化控制、配置审计、状态报告等

#### **⑥ 软件质量保证**
- 确保软件符合需求和性能要求
- 重点关注13种质量因素：正确性、健壮性、效率、完整性、可维护性等
- 措施：非执行测试（复审）、执行测试、程序正确性证明等

---

### 3. 软件规模估算有哪些方法？

1. **自顶向下估算法** - 从整体分解到详细
2. **自底向上估算法** - 从细节汇总到整体
3. **差别估算法** - 基于差异进行估算
4. **专家估算法** - 请专家多轮评估，求平均值
5. **类推估算法** - 基于类似项目进行估算
6. **算式估算法** - 使用数学模型进行估算

---

### 4. 规模估算的常用技术

1. **代码行技术** - LOC（代码行数）、KLOC（千行代码）
2. **功能点技术** - FP（Function Point）
3. **COCOMO2模型** - 估算工作量

---

### 5. 进度计划的常用表达工具

1. **Gantt图** - 甘特图，直观展示时间进度
2. **任务网络图** - 展示任务依赖关系

---

### 6. 什么是关键路径？有什么作用？

**定义**：项目里总耗时最长的任务链条

**特点**：链上任何一个环节拖了，整个项目就会延期

**作用**：
- 直接定死项目的最短完工时间
- 帮助把精力和资源盯在最影响工期的核心任务上
- 赶进度时，优先给这条链上的任务提速，就能最快压缩整体工期

---

### 7. 人员组织的关键问题

**关键问题**：确保团队成员必须以一种 **有意义且有效的方式彼此交互和通信**

**重要规律**：单纯靠增加人员 **并不能提高效率**
- 新增加人员会导致人与人之间的通信路径增加
- 这不仅不能提高生产率，反而会使其下降

---

### 8. 人员组织有哪些组织形式？

1. **民主制程序员组** - 民主讨论，集体决策
2. **主程序员组** - 由高手主导，其他人支持
3. **现代程序员组** - 结合两者优点的形式

---

### 9. 什么是软件质量？有多少个指标？

**定义**：软件与明确地和隐含地定义的需求相一致的程度

**换言之**：软件符合明确叙述的功能和性能需求、文档中明确描述的开发标准、以及所有专业开发的软件都应具有的隐含特征的程度

**指标数量**：共 **13种**

**具体指标**：
1. 正确性
2. 健壮性
3. 效率
4. 完整性
5. 可用性
6. 风险
7. 可理解性
8. 可维护性
9. 灵活性
10. 可测试性
11. 可移植性
12. 可再用性
13. 互运行性

---

### 10. 软件配置相关概念

| 概念             | 定义                                                         |
| ---------------- | ------------------------------------------------------------ |
| **软件配置**     | 软件过程中生产出的程序、文档和数据的统称                     |
| **软件配置项**   | 配置中的每一项                                               |
| **软件配置管理** | 在计算机软件整个生命期内管理变化的一组活动（跟踪和控制活动） |
| **基线**         | 通过了正式复审的软件配置项                                   |

---

### 11. 什么是CMM？有多少个等级？

**CMM**：软件能力成熟度模型（Capability Maturity Model for Software）

**用途**：主要用于评价软件机构的软件过程能力成熟度

**等级数**：共 **5个等级**

| 等级      | 名称       | 特征                     |
| --------- | ---------- | ------------------------ |
| **第1级** | 初始级     | 软件过程无序、不稳定     |
| **第2级** | 可重复级   | 建立了基本的软件管理过程 |
| **第3级** | 已定义级** | 软件过程已文档化并标准化 |
| **第4级** | 已管理级** | 软件过程可量化           |
| **第5级** | 优化级**   | 软件过程不断改进         |
